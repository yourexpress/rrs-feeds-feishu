Do AI coding agents struggle with non-REST APIs?

Microsoft · 2026-11-23 · 技术博客 / 每日精选

微软 1,356 次运行/6 模型实证：有文档时 REST/POST-only/RPC 三种 API 风格表现无差异，无文档时 RPC 成功率 0%、REST 93–97%。

Plenty of APIs skip REST conventions. Some send every write over POST, and some name every endpoint after an action, like /updateBin

or /deleteBin

. On paper, agents should have a harder time with those. REST maps the intent onto the HTTP method, so changing a record is a PATCH

and removing it is a DELETE

. In comparison, an RPC-style API makes the agent work out what each endpoint is called and what it does. We expected that to cost agents something, either in failed tasks or in extra calls and tokens.

It didn’t, at least when the agent had the docs. Across 1,356 runs with six models from two vendors, agents succeeded just as often with REST, POST-only and RPC-style APIs, at the same cost in failed calls and tokens. Without docs, REST won by a wide margin, because agents can guess REST URLs from convention and have no way to guess what a non-REST API calls its endpoints.

Where non-REST APIs could trip up an agent

“Non-REST” usually changes two things at once. It limits the API to GET and POST, and it replaces resource paths with endpoints named after verbs, and either change could cost an agent. A model that has seen a lot of REST might reach for DELETE

out of habit and get a 404. A model faced with a dozen verb-named endpoints might pick the wrong one, for example a full replace where a partial update was needed, and wipe data it was supposed to keep. If that happened, agents would complete fewer tasks or need more failed calls and tokens to get there, so we measured both.

One API, three styles

We built a fictional inventory API called Binstock, with bins and the items stored in them, so no model could have memorized it. We served it in three styles with identical data and behavior. Here’s the same partial update in each:

# rest

PATCH /bins/B-103

# postonly

POST /bins/B-103/update

# rpc

POST /updateBin?code=B-103
