Chopping a sentence into the numbered pieces a language model actually reads was supposed to be the part nobody had to think about. Set that arithmetic beside the matrix multiplications that make up the model’s real work and it looks like a rounding error, and for years it was treated as one. Hugging Face, in announcing a rebuilt version of its tokenizer library, said plainly that the tokenizer had not historically been the bottleneck, then listed when that stops being true: serving many requests at once, or processing long inputs over and over. What changed is not the chopping. It is everything downstream of it. Once the expensive half of a system gets fast enough, the cheap step in front of it stops being free, and the machine you paid for ends up waiting on the one you never measured.

The order of operations is fixed. Text arrives, an ordinary processor turns it into tokens, and only then can the graphics chips begin. In two serving engines, SGLang and vLLM, the chopping is done by quick libraries written in Rust or C++, but every call to them passes through Python, and Python has a rule — the global interpreter lock, or GIL — that lets one thread run Python code at a time. According to a post on the PyTorch blog by the LightSeek Foundation, that puts a single-file queue on CPU work sitting directly in the path of every request. At small scale nobody notices. The post says it began to hurt in production once serving was rearranged to make the GPUs very fast: reading a prompt on one set of machines and writing the reply on another, or spreading the specialised parts of a model across a whole cluster. Every microsecond spent behind that lock, in the post’s words, is a microsecond the accelerators sit idle waiting for input.
